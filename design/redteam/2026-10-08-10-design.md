## F1

Severity: BLOCKING

Status: defect

Claim: Fallback save migration produces a state that the new content-log invariant rejects.

Where: `design/10-design.md`, Content Epochs §7, "loadGame / Otherwise"; `design/20-contract.md`, core C26, §4 deserialize, and §10.2 save migration. The unchanged migration's envelope operation is also explicit in `src/engine/src/core/persistence/envelope.ts:193`.

Breaks when: A save has `formatVersion: 2`, `campaignVersion: "e2"`, and a last content entry `{ seq: 0, system: "content", from: "e1", to: "e2" }`. Load it on a host whose archive lacks e2 but whose default campaign e3 supplies a successful migration. This is the fallback the design explicitly preserves. Migration changes `kindState`, restamps `campaignVersion` to e3, sets `replayCompatible: false`, and preserves the action log. Its last content entry still ends at e2. Neither migration hook owns the envelope or log, and the specified fallback supplies no other log transition.

Consequence: The successful migration yields a state that C26 and deserialize must reject as `invalid_state`: `lastContent.to` is e2 while `campaignVersion` is e3. Even if load initially projects it, a subsequent deserialize of that persisted session or re-saved game rejects it. `replayCompatible: false` does not exempt a state from C26. The retained fallback and the new invariant cannot both hold as written.

Cost: Cheap to fix now, while content epochs are design-only; expensive after adopted saves exist, because this conflict spans persisted log semantics, migration, session hydration, and save round trips.

## F2

Severity: LOCAL

Status: defect

Claim: Story adoption accepts a node-kind change that strands an active session with no possible action.

Where: `design/10-design.md`, Content Epochs §5.4 and §5.5; `design/20-contract.md`, story-graph §8.1–§8.2. Existing behavior: `src/engine/src/kinds/story-graph/validateState.ts`, `scene.ts`, `advance.ts`, and `kind.ts`.

Breaks when: On e1, an active session is at choice node `square`, with `visitedCounts: { square: 1 }`, no variables or achievements, and no `endingId`. Valid e2 retains every referenced id but changes `square` to an ending node with `endingId: "home"`. No migration is needed. Every stated adoption predicate passes, and `validateState` accepts the unchanged state. Adoption changes neither envelope status nor `endingId` and runs no settle. A probe against the existing kind confirmed both campaigns validate, these compatibility predicates pass, state validation succeeds, available actions are `[]`, and the outcome remains nonterminal. The target's `no_reachable_choice` diagnostic is only a warning.

Consequence: The player receives an active scene with no actions. Submitting any choice rejects `not_a_choice_node`; the ending is never recorded because only the omitted settle would have reached it. The promised refusal of changes that could strand the player does not follow from the declared compatibility test.

Cost: Cheap to fix now and contained in the story-graph adoption contract; persisted adoptions later make the compatibility decision part of replay history.

## F3

Severity: STRUCTURAL

Status: defect

Claim: A client cannot obtain a scene and its localization table from a guaranteed common epoch.

Where: `design/10-design.md`, Clients §2 and Content Epochs §4–§5; `design/20-contract.md`, core §6 Scene, §7 SessionStore and session locking, and the current-epoch rule for `getStrings` immediately before §7.1.

Breaks when: Client A calls `getScene` on e1 and receives a choice with `labelKey: "choice.old"`. Before A calls `getStrings`, client B calls `resumeSession` on the same session, which adopts e2. The same choice on e2 uses `labelKey: "choice.new"`; e2's valid table contains that key and omits `choice.old`. This change satisfies story adoption. A's `getStrings` now returns e2's table, so its already-returned scene contains an unresolvable key. All operations respect the per-session lock: the race occurs between completed calls. Reading the table first permits the inverse interleaving.

Consequence: A conforming client can display missing action labels or changed wording for an older scene. Neither `Scene` nor `StringTable` carries an epoch or revision, and `getStrings` accepts only `sessionId`, so the client cannot detect this mismatch or request the table for its scene through the permitted store API. The new current-epoch rule invalidates the previous assumption that a session's table stays fixed.

Cost: Cheap to address before epoch delivery; expensive later because the missing consistency contract crosses session results, localization, client adapters, and any remote representation of those APIs.
